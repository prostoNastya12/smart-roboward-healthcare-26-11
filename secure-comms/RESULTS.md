# Secure communication pipelines: measured results

Generated by `node secure-comms/report.cjs` from [results.json](results.json). Do not edit by hand.

**Status of these numbers: measured on simulated devices with fictional data; attacks written by the team.** The cryptography is real (Ed25519, X25519, HKDF, AES-256-GCM, HMAC-SHA-256). The devices, trips and keys are fictional and created at run time. The network admission step in B and the adapter's capacity in the flood are models.

## Decision

**Adopted: I, Zero-trust relay.** It blocked 23 of 23 attacks, closed 3 of 6 known limits, and passed 9 of 9 legitimate cases.

How we got there. A to G are seven candidates, compared under a rule fixed before the first run: a pipeline that fails a legitimate case is out, then the most attacks blocked wins, then fewer supplier requirements, then fewer bytes. **G, Layered pipeline,** won with 22 of 23. H and I were then built on G to close what it left open. The team asked for the strongest design, so the platform uses I. Attacks were added and hardened after each review, so the counts are for the final suite and every pipeline was re-measured against it.

## Built on the winner: H, Layered pipeline with dual control

Everything in G. In addition the lift adapter requires a second signature from the clinical order system, independent of the dispatcher, naming the same robot and floor. Source: extension of g, added after the first results.

It blocked 22 of 23 attacks and 1 of 6 known limits: T20 (0 lift call(s) on a grant with no order behind it, 0 on re-issued grants naming another robot's key). Weakest point: Both the dispatcher and the order system would have to be compromised. Message timing remains visible.

## Built on the winner: I, Zero-trust relay

Everything in H. The fleet manager becomes a relay that is trusted with nothing: robot and lift adapter share their own encrypted session through it, the robot only accepts missions signed by the hospital, and the adapter keeps its own breaker. Source: built after the review and the challenge material, on top of h.

It blocked 23 of 23 attacks and 3 of 6 known limits: T20 (0 lift call(s) on a grant with no order behind it, 0 on re-issued grants naming another robot's key), T23 (The fleet manager carried the mission and the call and could read neither), T24 (20 of 20 legitimate calls served (100%), adapter refused 0 frames as overloaded). Weakest point: A compromised fleet manager can still stop relaying, which pauses robot deliveries, and message timing remains visible. The firewall rule is modelled.

## Fairness check: the simpler designs with a trip table

A, B, D and E are measured as pure mechanisms: the adapter knows which trips exist, and nothing else. A reviewer pointed out that this handicaps them. So we also measured them with an online trip table at the adapter, which tells it which robot and floor each trip was given. That table is itself a new integration between dispatcher and adapter. It is an online form of the same idea as F's signed grant, and with it D reaches F's count. G stays ahead in both readings.

## How to read the margin

- G is ahead of F partly through the encrypted channel (T01, T15) and the breaker (T14), and partly through checks at the adapter that are not about the wire at all (T16 to T19). Any design could add those four. They are in G because a lift call is only safe when the message and the situation are both right.
- T17 fails in A to F because none of them has a rule about which fields may be sent or stored. The test shows the absence of a rule.
- E loses T11 because its sessions have no idle timeout and a channel alone carries no message time. A short timeout would narrow that window.
- C runs the teammate's method M1 alone, as the plan says. Their full gate adds M2 to M4, which G reuses as its field allowlist and breaker.
- T15 checks that no key-agreement secret or exportable session key is kept. It does not attempt a decryption.
- A log signed by the adapter stops verifying if the adapter's key is replaced. Entries would need to name the key that signed them.

## Independent review

A second reviewer, who did not write the code, attacked an earlier version. It confirmed eleven findings. The important ones and what changed:

| Finding | What changed |
| --- | --- |
| An attacker on the network path could get a genuine robot isolated for good by holding its calls and releasing them together | One live session per device, refusals counted in a 10 second window, stale messages not counted, isolation ends after 60 seconds. Now attack T22 |
| An honest robot retrying a held call locked itself out | A retry is signed again with a fresh time. Now legitimate case L06 |
| Cutting the end of the audit log went unnoticed | The head of the log is exported to an outside witness on every entry. T16 now also cuts |
| A compromised robot could obtain a genuine answer under another robot's request ID and swap it in | Signed answers are bound to a hash of the exact request. T12 now also swaps |
| A retired robot that already held a ticket still worked in C, and T09 never tested it | T09 now gives the robot a real trip first. C lost that row |
| A private marker could be smuggled in the request ID | Envelope fields are validated and the log stores a fingerprint. T17 now also tries the request ID |
| A revoked certificate kept working on an open connection | Both ends check the peer's certificate on every record |
| The fleet manager could re-submit a held call within 30 seconds | Each signed call is accepted once |
| A and B failed the retry case only because the test harness gave them no retry cache | They have it now. T03 also replays under a new request ID |
| A flood sent straight to the adapter bypasses the breaker | Not fixed. Reported as limit T24 |
| The fleet manager reads trip and floor | Not fixed. Reported as limit T23 |

## Second review, of H and I

The same kind of reviewer attacked the two new pipelines. It confirmed twelve findings. The important ones and what changed:

| Finding | What changed |
| --- | --- |
| The fleet manager could relabel a robot's genuine calls so the adapter refused them, isolating the robot and blaming it in the signed log | The adapter no longer uses anything the relay says about a call. Refusals count only for a fresh call from the robot itself. T22 now includes this |
| The fleet manager could not read the call but still read trip, floor and destination from the mission it delivers | Missions, grants and orders now travel sealed to a one-time key of the robot. T23 and the who-sees-what table now include the mission leg |
| Answer sizes differed by outcome | Sealed requests and answers are padded to a fixed step |
| A genuine earlier mission could be replayed inside its ten-minute window | A sealed mission opens once, and missions are numbered per robot. T25 now includes this |
| A compromised dispatcher working with one robot could re-issue a real grant under that robot's key | The key in a grant must be the key the hospital certified for the named robot, and a trip yields one lift call however many grants exist. T20 now includes this |
| Several robots calling at the same moment failed | Exchanges on one session take turns. Now legitimate case L09 |
| An attacker with the adapter's key could rebuild the log, and a key change broke verification | The outside witness only appends, and each entry names its signing key |
| Three attacks held back a handshake frame instead of the call in tunnelled pipelines, so they tested nothing there | T10, T11 and T22 now start from open connections |
| A lost answer to a held call became a counted refusal | The exact message answered last gets the same answer again |
| The direct flood was stopped only by the modelled firewall rule | Not fixed. A flood from the wired path that poses as the relay is limit T28 |
| Five honest wrong-floor calls in ten seconds isolate a robot for a minute | Kept as designed, and documented here |

## What the adopted pipeline needs

Everything in G:

- Hospital certificate authority
- Signing service at the dispatcher
- Robots that hold a key, sign, and support authenticated channels
- Fleet manager with a per-robot breaker
- Lift adapter that verifies grants, checks lift status and signs its log
- Status feed from facilities
- Presence sensor at the lift lobby

And in addition:

- Clinical order system that signs each delivery order
- Robots that check a signed mission before moving
- Lift adapter that ends the robot's encrypted session itself
- Firewall rule: only the relay's address reaches the lift adapter

Weakest point: A compromised fleet manager can still stop relaying, which pauses robot deliveries, and message timing remains visible. The firewall rule is modelled.

A hospital that cannot get all of this can start lower in the table. Each row above says what it would be giving up.
